## Context

Users managing Karabiner Elements hyper key + sublayer configurations currently edit raw JSON files (often 1000+ lines). No purpose-built visual editor exists for this pattern. The app must run as a single HTML file opened directly in a browser -- no server, no build step. The target users are macOS power users who already have a working Karabiner config and want a faster way to tweak their sublayer bindings.

The Karabiner JSON structure is well-defined: complex modifications live in `profiles[].complex_modifications.rules[]`, where each rule contains manipulators with `from`, `to`, `conditions`, and variable-based sublayer activation. The app needs to parse this structure, present it as editable sublayers, and serialize changes back.

## Goals / Non-Goals

**Goals:**
- Single HTML file, zero server dependencies, openable via `file://`
- Parse Karabiner complex modification rules to extract hyper key + sublayer structure
- Purpose-built UI for the hyper+sublayer pattern (not a generic JSON editor)
- Edit sublayers and bindings through form controls and a visual key grid
- Copy-paste JSON workflow (paste in, edit, copy out)
- Clean, minimal UI that scales to many sublayers without clutter

**Non-Goals:**
- Full Karabiner JSON editor (only hyper/sublayer rules are editable; other rules pass through untouched)
- Direct filesystem access (future feature, not V1)
- Support for non-hyper complex modifications (leader mode, duo layers, simultaneous keys)
- Mobile/responsive design (desktop-only is fine for a keyboard config tool)
- Build tooling, package management, or framework CLI

## Decisions

### 1. Single HTML file with inline everything

**Decision:** Ship as one `index.html` with inline CSS and JS. No external dependencies, no CDN links.

**Rationale:** The primary constraint is "open in browser, just works." CDN links fail offline and add CORS/CSP complexity with `file://`. A single file is the simplest distribution model -- copy it, bookmark it, done.

**Alternative considered:** Multiple files (separate `.css`, `.js`) -- rejected because it complicates distribution and `file://` can have issues with relative imports. Also considered CDN-loaded frameworks -- rejected for offline reliability.

### 2. Vanilla JS + Web Components (no framework)

**Decision:** Use vanilla JavaScript with native Web Components (`customElements.define`) for UI composition. No React, Vue, Svelte, or other framework.

**Rationale:**
- Zero build step requirement eliminates all bundler-based frameworks
- Web Components provide real encapsulation (shadow DOM for styles) and composability
- Native browser APIs are sufficient for this scale of UI (< 20 interactive elements visible at once)
- No version conflicts, no CDN dependency, no framework churn
- The app's state is simple: one config object with sublayers and bindings

**Alternative considered:** Preact via CDN (small, JSX-like) -- rejected because CDN breaks offline use and JSX requires transpilation. Alpine.js -- viable but adds unnecessary abstraction for this scope.

### 3. State architecture: single reactive store

**Decision:** A single JavaScript object holds the entire parsed config. A simple pub/sub (EventTarget-based) notifies components on changes. No immutable state, no reducers -- just a mutable object with change events.

**Rationale:** The data model is small and tree-shaped (config → sublayers → bindings). Direct mutation with event notification is the simplest approach that still keeps UI in sync. Overcomplicated state management adds no value at this scale.

### 4. JSON parsing strategy: structural pattern matching

**Decision:** Parse the Karabiner JSON by walking `rules[].manipulators[]` and identifying hyper key patterns by structure:
1. Find the hyper key activator (sets `hyper` variable to 1 on caps_lock/tab press)
2. Find sublayer activators (sets `hyper_sublayer_X` to 1, conditioned on `hyper == 1`)
3. Find sublayer bindings (conditioned on `hyper_sublayer_X == 1`)
4. Collect unrecognized rules as pass-through (preserved but not editable)

**Rationale:** The hyper/sublayer pattern uses consistent variable naming conventions (`hyper`, `hyper_sublayer_*`). Pattern matching on variable names and condition structures is reliable for configs generated by mxstbr, karabiner.ts, or hand-written following the convention. Pass-through for unrecognized rules ensures the tool doesn't destroy non-hyper config.

### 5. CSS: inline with CSS custom properties

**Decision:** All styles inline in `<style>` tag. Use CSS custom properties for theming. CSS Grid for layout. No CSS framework.

**Rationale:** Keeps the single-file constraint. Custom properties enable future dark/light theme toggle with minimal code. CSS Grid handles the keyboard visualization layout naturally.

### 6. Keyboard visualization: CSS Grid, not SVG/Canvas

**Decision:** Render the key grid as a CSS Grid of `<button>` elements, not SVG or Canvas.

**Rationale:** Buttons are naturally interactive (click, hover, focus, keyboard accessible). CSS Grid handles the irregular keyboard layout well enough for a grid view (we're showing a simplified grid, not a photorealistic keyboard). SVG would require custom hit detection; Canvas would lose accessibility.

## Risks / Trade-offs

- **[Risk] Unfamiliar variable naming conventions** → The parser assumes `hyper` and `hyper_sublayer_*` variable names. Configs using different names (e.g., Goku-generated) won't parse correctly. → **Mitigation:** Document supported naming conventions. V1 targets mxstbr-style configs. Future: allow user to specify variable name prefix.

- **[Risk] Large configs may have slow paste/parse** → Typical hyper configs are 1-5K lines, which is fine. Extreme configs (Vonng's 22K+ lines) could cause a brief freeze. → **Mitigation:** Parse in a `requestIdleCallback` or show a loading indicator. Acceptable for V1.

- **[Risk] Single HTML file may grow large** → Inline JS + CSS + HTML could reach 50-100KB. → **Mitigation:** This is acceptable. A 100KB HTML file loads instantly and is smaller than most web pages.

- **[Trade-off] No framework = more boilerplate** → Web Components require more ceremony than React/Vue for simple forms. → **Accepted:** The total UI surface is small enough that the extra boilerplate is manageable and avoids framework lock-in.

- **[Trade-off] No undo/redo in V1** → Users editing via UI have no undo beyond re-pasting original JSON. → **Accepted:** The paste-in/copy-out workflow means the original JSON is always available. Undo/redo can be added later.
